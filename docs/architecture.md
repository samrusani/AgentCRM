# Architecture

AgentCRM runs as two local processes over one SQLite file.

- `apps/server`: a Fastify API on http://127.0.0.1:4720, an in-process job worker, a CLI, and an MCP server over stdio. The API server is the primary writer. The MCP server runs as a separate local process against the same SQLite file and runs its own worker tick, so runs it starts advance even when the API server is down; both writers use short immediate transactions through the same action service. The API server watches SQLite's data_version and relays commits from the MCP process as server sent events.
- `apps/web`: a React app served by Vite on http://127.0.0.1:5173 in development, proxying `/api` to the server.

The database lives at `data/agentcrm.db` relative to the repository root, in WAL mode. The `data/` folder is created on demand and never committed.

## The action service

All mutations flow through one module layer, `apps/server/src/actions/`. A route handler, a job, a CLI command, and an MCP tool all call the same action functions. An action:

1. Validates input with zod.
2. Checks workspace scope.
3. Checks `expectedVersion` on versioned records and fails with `version_conflict` on mismatch.
4. Applies the change in a short transaction.
5. Writes an `audit_event` row in the same transaction.

Reads can use shared query helpers directly. Writes never bypass actions.

## Data model

IDs are prefixed strings, for example `per_a1b2c3`, generated from random bytes. Prefixes: `wsp` workspace, `per` person, `org` organization, `pip` pipeline, `stg` stage, `opp` opportunity, `act` activity, `tsk` task, `clm` field claim, `run` run, `stp` run step, `apr` approval, `job` job, `aud` audit event, `evt` stage event, `fur` follow-up rule. Timestamps are ISO 8601 UTC strings.

Connector secrets live only in the local database's secret column: they are excluded from every API response (masked to the last four characters), from audit detail, from logs, and from SSE payloads. Id prefixes for the new tables: `con`, `imp`, `row`.

Indexes at minimum: person(workspace_id, last_name), person(workspace_id, email), person(workspace_id, linkedin_url), person(workspace_id, x_url), organization(workspace_id, domain), organization(workspace_id, linkedin_url), opportunity(workspace_id, pipeline_id, stage_id), task(workspace_id, status, due_at), activity(workspace_id, entity_type, entity_id, created_at), field_claim(workspace_id, entity_type, entity_id), job(status, run_at), plus expression indexes on lower(email) for person and lower(domain) for organization, which the duplicate checks and import dedupe rely on.

Profile URLs are first class fields (migration 018): person.linkedin_url holds the canonical `/in/<id>` URL, person.x_url the canonical x.com profile URL, organization.linkedin_url a canonical `linkedin.com/company/<slug>` URL (host lowercased, path segment kept as is, query and trailing slash stripped; http or https only, no userinfo or port, for all three; a URL that does not parse as that shape is rejected on edit). Accepted limit: capture and lookup compare the stored canonical strings, so two spellings of one id that differ only in percent encoding stay two people there, while lead capture's normalization merges them. The migration backfills each column from the entity's newest `field_claim` for that field whose value passes the same normalization, and these columns are what capture, lookup, and import dedupe match against from then on; claims remain the evidence trail. Both sheets show and edit the fields like any other.

## Run state machine

`queued -> running -> waiting_approval | paused -> running -> succeeded | partial | failed | cancelled`

Rules:

- `waiting_approval` means a pending approval row references the run. Deciding the approval moves the run forward.
- Pause and cancel are user actions. Cancel is final.
- Counts report `{ processed, found, flagged }` and update as steps complete. A run that cannot meet its requested scope finishes as `partial` with honest counts, never with invented results.

## The simulated demo run

No model provider is wired up yet, so `kind: "demo_research"` exists to exercise the machinery honestly. The job worker advances a scripted set of steps (check existing records, search sources, extract candidates, qualify) on a timer, roughly one step per second, generating a handful of synthetic candidate field claims and new person records tagged `demo-candidate`. The final step creates an approval of kind `shortlist` and the run enters `waiting_approval`. Approving creates draft outreach activities (kind `email_draft`, clearly labelled as demo drafts); rejecting finishes the run as `cancelled`. Every UI surface labels these runs as simulated.

## Apify connector

Apify is the first real external provider. The user connects their own Apify account with an API token in Settings; AgentCRM then lets them run any Actor from the Apify store, with the results staged for review before anything enters the CRM. Apify charges the user's own account. Every run passes `maxItems` and a timeout to Apify as platform side caps, but Apify enforces `maxItems` only for pay per result actors, so for other pricing models the timeout is the effective limit. AgentCRM cannot hard cap spend for every pricing model and the UI says so rather than promising otherwise.

Flow for a run of kind `apify_scrape`:

1. Validate the connector, the actor id, and the input. The run stores `{ actorId, input, maxItems }` in its scope.
2. Mark the start attempt in the run scope, then start the actor run through the Apify API and record the Apify run id in the run scope, so polling survives a worker restart. If a start attempt's outcome is unknown (lost response, unparseable body, or a crash before the id was saved), the run fails and tells the user to check their Apify console; a retry never sends a second billed start.
3. Poll the Apify run until it finishes, with a configurable timeout (default 10 minutes). Elapsed time shows in the step detail.
4. Fetch dataset items up to `maxItems` (default 100, hard max 1000) and stage them as import rows with the raw item preserved.
5. Map common lead fields heuristically (name parts, email, company, domain, website, title, location, LinkedIn URL). Rows with neither a name nor an email are marked invalid with a reason. Unmapped keys stay in the raw column.
6. Dedupe against existing people (normalized email, then name plus organization) and organizations (domain, then name). Matches are marked duplicate, never merged silently.
7. Create an approval of kind `import_review` with honest counts (fetched, staged, duplicates, invalid) and a sample, and enter `waiting_approval`.
8. Approve: accepted rows create people and organizations plus field claims (source_type `apify`, source URL pointing at the Apify run, extraction method recording the actor id), all tagged `apify` and `via-<runId>`. Reject: the batch is rejected and nothing is created. Either way the run finishes with honest counts; a failed or aborted Apify run finishes `failed` (or `partial` when rows were already staged), and a run with nothing left to review finishes `partial` with no approval. The run never fabricates rows. Cancelling, timing out, or failing for good also makes a best effort request to abort the remote actor run; pausing stops local processing while the remote run continues, and the UI says so.

Policy: configuring connectors and deciding approvals are human actions through the UI. Runs started through MCP or the agent endpoint may only use actor ids on the connector's allowlist (a settings array edited in the UI), and at most one agent started Apify run may be active at a time. Runs started by the user in the UI can use any actor they pick. The Apify API token is sent only to api.apify.com, never to a model or a page.

The Apify base URL is `https://api.apify.com`, overridable with `AGENTCRM_APIFY_BASE` for tests. Key Apify endpoints used: `GET /v2/users/me` (token check), `GET /v2/store?search=` (actor search), `GET /v2/acts/:actorId` (actor detail, example input when present), `POST /v2/acts/:actorId/runs` (start), `GET /v2/actor-runs/:runId` (poll), `GET /v2/datasets/:datasetId/items` (results). Actor ids in the `username~actor-name` form are URL encoded.

## LinkedIn lead capture

Paste a LinkedIn post URL and the agent captures leads from it through the user's own Apify account: who engaged with the post (reactions and comments), and the people and organizations named in the post text itself, because posts are often lists of angels, family offices, or funds. Captured people are staged, the new ones optionally enriched with profile details through one more Apify actor run, and one import review gates everything. The feature composes four store actors, configurable per workspace with these defaults (store prices noted as of their stated date, charged by Apify to the user's account):

| Role | Default actor | Default input shape | Price hint |
| --- | --- | --- | --- |
| Post text | `apimaestro/linkedin-post-detail` | `{ post_urls: [postUrl] }` | from 5.00 per 1,000 results (2026-11-03) |
| Reactions | `harvestapi/linkedin-post-reactions` | `{ posts: [postUrl], maxItems }` | from 1.50 per 1,000 results (2026-11-02) |
| Comments | `harvestapi/linkedin-post-comments` | `{ posts: [postUrl], maxItems }` | from 1.50 per 1,000 results (2026-11-02) |
| Profile enrichment | `harvestapi/linkedin-profile-scraper` | `{ queries: urls, profileUrls: urls, usernames: urls }` | from 4.00 per 1,000 profiles (2026-11-02) |

The post text actor documents `/posts/` URLs and bare activity ids as input; for a `/feed/update/urn:li:activity:<digits>` URL the server sends the bare numeric id instead, and other urn forms go as given (an actor that rejects them ends the post step with the actor's own message). Reading the names out of the post text is model work: it uses the workspace's active model provider through the normal adapter, so it needs a ready provider and records a `model_call` row like chat and drafting do, with the estimated cost synced into the run counts. The post text is untrusted content and is handled as data end to end: it is sanitized (zero width characters stripped, NFKC normalized, fence lookalike tags replaced), wrapped in a fenced block with instructions-are-data framing, and the extraction call has no tools. The model must answer only the JSON schema `{ entries: [{ kind: 'person' | 'organization', orgKind?, name, title?, company?, location?, linkedinUrl?, quote }] }` (quote is a verbatim snippet of at most 200 characters; `orgKind` 'fund' or 'company' sorts funds, venture firms, and family offices from operating companies). The answer is zod validated; providers that only offer `json_object` get one repair retry, schema capable providers do not. Every entry is then verified against the post text actually sent: an entry whose name, quote, or stated profile URL does not occur in the text is dropped and counted, so a hallucinated or injected lead is never staged or enriched, and a person link that is not an `/in/` profile path is removed from the entry. Post text is cut at 15,000 characters with a note. Verified entries are capped at `maxPeople` with a note. Once staging has consumed them, the extracted entries are removed from the run scope (and on any earlier terminal state), the scope key is excluded from run list reads, and `crm_get_run` never returns extracted text, so post content reaches no model or agent facing surface; it lives on only in the import rows the human reviews. The post author, which the post actor returns structured, is staged as one more person row without model work.

The enrichment input carries the url list under three field names at once (`queries`, `profileUrls`, `usernames`) so the common store actors accept it without per actor configuration; actors ignore fields they do not define. A custom actor id that rejects this shape ends the enrich step with the actor's own message in the ledger, and the run still goes to review. The actor ids live in the Apify connector settings as `leadCapture: { postActor, reactionsActor, commentsActor, profileActor, companyActor }`, editable in the Apify card (`companyActor`, default `harvestapi/linkedin-company`, is used by organization enrichment, not by lead capture itself), and `PUT /api/connectors/apify` accepts a `leadCapture` object alongside `token` and `allowlist`, or alone. Each field is optional and per field: a sent id is normalized like an allowlist entry and stored, an empty string resets that field to its default, and a field left out keeps its value.

Run kind `lead_capture`, scope `{ postUrl, sources, maxPeople, enrich, enrichLimit, actors, calls, batchId? }`:

- `postUrl`: must start with `http://` or `https://` on `linkedin.com` or a subdomain and match a post shape: `/posts/<slug>-activity-<digits>`, `-ugcPost-<digits>`, or `-share-<digits>` (with optional suffix and query), or `/feed/update/urn:li:activity:<digits>`, `urn:li:ugcPost:<digits>`, or `urn:li:share:<digits>`. Anything else is rejected with a sentence naming the accepted shapes. Max 500 characters. The URL is passed to the actors as given (the web form prepends `https://` to a schemeless paste before sending).
- `sources`: non empty subset of `['post', 'reactions', 'comments']`. Default for user started runs: all three when a ready model provider is active, otherwise reactions and comments. Agent started runs default to reactions and comments only; the post source, which spends extra actor and model money, must be asked for explicitly. Starting a run with `post` in the sources requires a ready model provider; the validate step re-checks it, drops the post source with an honest detail when the provider stopped being ready, and names the provider and model in the detail when the active model changed since start.
- `maxPeople`: per source cap passed to each engagement actor as `maxItems`, default 50, hard max 500.
- `enrich`: boolean, default true. `enrichLimit`: how many new people may be enriched, default 25, hard max 200.
- `actors`: the three resolved actor ids, frozen into the scope at start so a settings edit mid run changes nothing.
- `calls`: per actor call state, keyed `post`, `reactions`, `comments`, `enrich`. Each call carries `{ actorId, startAttemptedAt?, apifyRunId?, datasetId?, startedAt?, finished?, abortRequested?, itemCount? }` and follows the exact money discipline of `apify_scrape`: the start attempt is marked in its own transaction before the request leaves the process, and that transaction re-reads the scope and backs off when another tick already marked it; an unknown start outcome is never retried; a restart polls the saved run id instead of starting again; rate limited before start clears the marker and retries; every terminal path, `partial` included, makes a best effort abort request for every unfinished remote call. An unknown outcome on an engagement call fails the run; on the enrich call it is soft (see step 6). Lead capture runs in a worker lane of its own, separate from plain Apify imports, so its extraction step's model call (which can take a minute or two) never pauses the polling of other Apify runs; it only queues behind other lead captures.

Steps:

1. Validate the connector, the URL, the sources, and the limits, including a ready model provider when `post` is selected (when it stopped being ready since start, the post source is dropped with an honest detail instead of failing the run, and the other sources continue).
2. Read the post through Apify (when `post` is not in `sources`, the step completes with a detail saying it was skipped and why; a failure here is soft like enrichment: the engagement sources continue and the detail says what was lost).
3. Scrape reactions through Apify (same skip rule; a failure here fails the run when reactions was the only source, otherwise it is soft).
4. Scrape comments through Apify (same rules as reactions).
5. Extract people named in the post: one fenced model call over the post text as described above (skipped without `post`). A model failure, refusal, or unreadable post dataset is soft while another selected source is still healthy: the step completes with what happened and the engagement people still go to review. When the post is the only selected source (or every other source already failed), a post that cannot be read fails the run. Pausing mid call never repeats the billed call: the outcome is saved whatever the run state and resumed from. The verified entries are kept in the run scope only until staging consumes them; each entry keeps its `quote`, shown to the reviewer in the batch rows.
6. Stage people from the post: one import row per unique person across all sources, merged only by normalized profile URL (host lowercased, the `/in/<id>` segment kept as is, query and trailing slash stripped). An item without a profile URL becomes its own row and never merges with anything, so two same named people stay two visible rows. Engagement mapping reads every person field from the item's `actor` object when it exists, else every field from the `author` object (`name`, `headline`, `profile_url`), never mixing the two; a profile URL is kept only when it parses as http or https on linkedin.com or a subdomain (extracted linkedinUrl values pass the same check). The post author becomes a row mapped from the post item's `author` object. Extracted `organization` entries become organization rows: `mapped.kind` is `organization`, the name goes to `company`, they are valid without a person name, and a `linkedin.com/company/` link the verification kept (it must occur in the post text) rides along as the row's `linkedinUrl`; accepting the row writes it to the organization's `linkedin_url` column with the usual claim. The raw column keeps the source items plus a `sources` array (`{ kind: 'reaction', reactionType }`, `{ kind: 'comment', commentary }`, `{ kind: 'post_author' }`, and `{ kind: 'post', quote }` with text cut to 200 characters). A person row with neither a name nor a profile URL is invalid with a reason, and an organization row without a company name is invalid. When a source's item count equals `maxPeople`, the step detail says the cap was reached and more engagement may exist. An engagement dataset that cannot be read at this step is soft when another source produced something: what exists is staged and the detail says what was lost. `fetched` counts unique rows, not items; the per source item counts live in the step detail and in `calls.*.itemCount`, and `requested` is `maxPeople` times the number of sources, plus one for the author when the post is a source. Batch `source_kind` is `lead_capture` (migration 010 widens the CHECK with the usual in place rebuild), `source_ref` is `{ postUrl, actors, apifyRunIds }`.
7. Check for duplicates before any enrichment money is spent: the Apify import rules, plus a match against existing people's `linkedin_url` column, plus a match against rows staged in another pending import of the same workspace (a batch still staging or awaiting review whose run is still open), each with its reason on the row. Organization rows dedupe against existing organizations by domain, then normalized name. A person the capture cannot identify by profile URL or email, such as a hand created person with neither, is not caught here; the step detail states the rule rather than overpromising.
8. Enrich new profiles through Apify (completes as skipped when `enrich` is false, or when no staged, non duplicate person row has a profile URL; organization rows are never enriched). Takes the first `enrichLimit` staged person rows with profile URLs, one batched actor run for all of them, never one run per person. An enrichment failure is soft: a permanent provider error, timeout, failed remote run, or unknown start outcome completes the step with the honest sentence (including the check your console sentence for unknown outcomes), requests the remote abort, and the staged rows still go to review without enrichment data.
9. Merge enriched details: an output item that carries a profile URL or `publicIdentifier` matches only by that key; the normalized name fallback applies only to items with neither, so a lookalike profile cannot attach its email to the wrong person. Enrichment fills empty mapped fields only (title, company, location, email, name split), reading flat fields heuristically plus the nested shapes `location.linkedinText`, `currentPosition[0].companyName`, and `headline`; the domain comes only from explicit company domain or company website fields, never from a personal website. The enrichment item is kept in the row's raw under `enrichment`. Unmatched output items are counted in the step detail and dropped. Dedupe runs once more, including against other pending imports, because an enriched email can reveal an existing or already staged person. Person rows still without a name and an email are marked invalid.
10. Request one `import_review` approval with the same counts as other imports; the payload carries `postUrl` and `actors`, and its sample rows include name, email, company, title, profile URL, and the row kind, so organization entries are visible as organizations. Approve: accepted rows create people, organizations (an organization row creates or matches just the organization), and field claims with source_type `apify`, source URL set to the post URL stripped of query and fragment, extraction method per claim naming what produced that field: `lead_capture:<actorId>` for actor sourced fields and `lead_capture:model:<provider>:<model>` for fields read out of the post text. Tags `linkedin-leads` and `via-<runId>`; rows whose email or LinkedIn profile now matches a person added after staging are skipped as duplicates at accept time. Reject: nothing is created.

Policy, matching the Apify section: a run started by the user in the UI may use the configured actor ids as they are. A run started through MCP or the agent endpoint requires every involved actor id (the selected sources plus enrichment when on) to be on the Apify allowlist, and counts against the same one active agent started Apify run limit. MCP gains the tool `start_lead_capture` taking `{ postUrl, sources?, maxPeople?, enrich?, enrichLimit? }`, subject to those rules. `POST /api/runs` accepts kind `lead_capture` with the same scope fields.

The run never promises a spend cap it cannot enforce: `maxItems` caps pay per result actors and the run timeout caps the rest, and the UI repeats the Apify section's sentence about that. Prices shown anywhere are store listing hints dated 2026-11-02, not invoices.

## Field enrichment

A person sheet with a LinkedIn profile saved gets one Enrich button. Clicking it starts a run of kind `enrich_person` (scope `{ personId }`, origin `user`, started only from the web UI in this version; neither MCP nor the agent endpoint can start one) that makes exactly one Apify call: the lead capture profile scraper actor (`settings.leadCapture` profile entry, same default) with the person's `linkedin_url` as its single target and `maxItems` 1, under the same money discipline as `apify_scrape` (compare and set start marker so a retry never starts a second billed run, poll, timeout; the actor id is recorded in the run scope). Guards, checked at start with an honest validation message: the Apify connector must be ready, the person must exist and have a `linkedin_url`, and only one open `enrich_person` run may exist per person.

The run writes nothing to the person. The returned item must name the target: one of the item's own profile keys has to normalize to the person's `linkedin_url`, compared without regard to the id's case because scrapers fold case (everywhere else LinkedIn ids stay case exact); keys that merely echo the request input, such as `inputUrl`, are ignored by this gate, so an item for another profile cannot pass by echoing what it was asked for. A non matching item fails the run with a step detail saying the scraped item named a different profile, and nothing is suggested. A matching item is read through `mapProfileItem`, and a suggestion is kept for each of `title`, `location`, and `email` whose mapped value is non empty while the person's field is empty at that moment. Scraped text is untrusted: suggestion values are scrubbed exactly like capture input (zero width, bidi, control characters, and NUL stripped), a value over 200 characters is dropped rather than cut (a truncated value could read as a different valid one), a value that would not survive the same validation as a manual edit of that field is not suggested, and an email already on another person (case folded) is not suggested. `scope.suggestions` stores `[{ field, value }]` and the final step detail says how many fields were suggested, or that every field was already filled or the profile offered nothing new. The suggestions and the frozen profile URL are excluded from agent facing run reads (`crm_get_run` and the agent run listing), like extracted post text, so scraped text reaches no model or agent surface before a human accepted it. Company, website, and phone are out of scope in this version and the sheet says nothing about them. Cancelling in the window between the start marker and the recorded Apify run id leaves a possibly billed start whose outcome is unknown; the run's final detail says so instead of staying silent.

Suggestions are reviewed on the person sheet, not applied by the run:

- `GET /api/people/:id/enrichment` answers `{ run, suggestions }` for that person's newest `enrich_person` run (null when none). `run` carries id, status, startedAt, `detail` (the final or failing step's detail, null while running), and `suggestedCount` (how many suggestions the run produced in all); `suggestions` holds only the pending ones. The client needs no memory of its own: pending rows render the list, a succeeded run with `suggestedCount` 0 renders the detail as a muted line, a succeeded run whose suggestions were all accepted or dismissed renders nothing, and a failed run renders its detail as a muted line until the next run starts.
- `POST /api/people/:id/enrichment` takes `{ runId, field, expectedVersion }` and accepts one suggestion: the run must belong to this person, be succeeded, and be the person's newest enrich run, the suggestion must still be pending, the person's field must still be empty, and the person's `linkedin_url` must still equal the run's frozen profile URL (each mismatch answers 409 `conflict`, so a suggestion scraped from an old profile never lands after the URL changed). In one transaction it writes the field through the normal update path and a `field_claim` (`source_type` `apify`, source URL the person's `linkedin_url`, extraction method `enrich:<actorId>`, status `imported`), marks the suggestion accepted in the run scope, and emits `record_updated`.
- `DELETE /api/people/:id/enrichment?runId=` dismisses the run's remaining pending suggestions, so the sheet shows nothing until the next enrich run.

Accepting and dismissing cost nothing; the money was spent by the one scrape. The sheet's button area carries the honest line that the run bills one profile scrape on the user's Apify account, and the suggestion rows show the value exactly as scraped.

Organizations enrich the same way with one difference: identity. An organization sheet gets the same Enrich button (guards: Apify ready, the organization exists, one open run per organization), starting kind `enrich_organization` (scope `{ organizationId }`, user origin only, no MCP tool, agent origin rejected) that makes exactly one call to the company lookup actor (`settings.leadCapture.companyActor`, default `harvestapi/linkedin-company`) under the same money discipline. When the organization has a `linkedin_url`, the input is `{ companies: [url] }` and the returned item must name that URL (slug compared without regard to case), else the run fails as a different company; the frozen target is that URL. When it has none, the input is `{ searches: [name] }` with the organization's name, the first item IS the candidate with no identity gate possible, and the frozen target is the name; the step detail names the company the lookup returned so the human can judge the match before accepting anything. Suggestions cover `linkedinUrl` (canonicalized company URL, only when the field is empty), `domain` (the hostname of the item's website, only when empty), and `location` (the headquarters text, only when empty), scrubbed, bounded, and validated exactly like person suggestions. The accept, dismiss, and GET endpoints mirror the person ones at `/api/organizations/:id/enrichment` with the same rules: newest succeeded run only, field still empty, and the frozen target must still match the organization (its `linkedin_url`, or its name in name mode), each mismatch 409 `conflict`; accepted values write the field plus a claim (`source_type` `apify`, extraction method `enrich:<actorId>`). The claim's source URL is evidence, so it is never guessed: in URL mode it is the frozen target URL itself, never a page read from the item, so a gate pass through a secondary key cannot attribute evidence to another company's page; in name mode it is the item's own canonical page, or null when the item named none, and never the organization's current link. Any page link read from an item is canonicalized and length bounded by the company URL helper (over 500 characters is refused) before it can reach a step detail, the run scope, or a claim, and an identifier key that cannot be percent encoded (a lone surrogate, for example) counts as absent in both the person and the organization identity checks instead of crashing the read step. `scope.suggestions`, the frozen target, and the item's source URL are excluded from agent facing run reads, and agent reads of both enrich kinds blank every step detail (statuses stay), because a name mode detail names the scraped company and scraped text reaches no agent surface before a human accepted it. Accepted limit, stated on the sheet by the step detail rather than hidden: a name lookup can return the wrong company for an ambiguous name; nothing is written until a human accepts a field.

Post links stay a documented limit: tagged companies in a LinkedIn post are links on linkedin.com, but every cookie free post actor returns plain text only, and the one store actor exposing mention structure requires the user's LinkedIn session cookies and documents person mentions only, so lead capture organization rows carry a page link only when the URL occurs in the post text, and organization enrichment is the supported way to find the page afterwards.

## Browser capture extension

A Chrome extension (`apps/extension`, Manifest V3, plain TypeScript bundled with esbuild and typechecked with tsc, no runtime dependencies) adds one "Add to AgentCRM" button to LinkedIn profile pages and X profile pages. Clicking it reads the profile the user is looking at and sends it to the local server, which creates the person with field claims. Nothing leaves the machine: the extension talks only to the configured base URL (default `http://localhost:4720`) and is loaded unpacked from the repository folder.

The extension captures exactly one profile per click and runs nothing in the background. It reads only what the page already shows the signed in user. That is the whole design: user initiated, one profile at a time, no crawling, no feeds, no automation.

### Capture token

Any web page the user visits can attempt a `fetch` against localhost, so the capture write path is authenticated. The server keeps a SHA-256 hash of one capture token in `workspace.settings.capture` (`{ tokenHash, createdAt }`), never the token itself. `POST /api/capture/token` generates a token (`cap_` plus 43 base64url characters from 32 random bytes), stores its hash, and returns the plaintext once; it is not readable again, and generating again rotates it, invalidating the old one immediately. The Settings card shows it exactly once with a copy control. `POST /api/capture` and `POST /api/capture/verify` require `Authorization: Bearer <token>`; the presented token is hashed and compared with `crypto.timingSafeEqual`. A missing, wrong, or never generated token answers 401 `unauthorized`. These two routes are the only token guarded routes; everything else stays loopback only as before (the loopback Host check applies to these too).

The token management routes take no body, and a cross site page could otherwise hit them with a fire and forget POST that needs no CORS preflight (it could not read the answer, but it could rotate the token out from under the extension). So the server also refuses any state changing request (anything but GET, HEAD, OPTIONS) that carries an `Origin` header naming a non loopback web origin, with 403. Requests without an `Origin` (the CLI, MCP, curl), same machine web origins, and browser extension origins are unaffected. The web app also listens for the `record_updated` frame with entityType `capture_settings`, which the token routes emit, so the Settings card reflects a rotation it did not make.

### Capture endpoint

`POST /api/capture` body (zod, strict): `{ source: 'linkedin' | 'x', url, name, headline?, company?, location?, handle?, bio?, website?, email?, phone? }`. `name` is required (the extension always has one: it falls back to the profile id or handle). Limits: url and website 500, name, headline, company, location 200, handle 30, bio 2,000, email 254 and must parse as an email (the extension drops a scraped string that does not look like one before sending), phone 40 and it must contain a digit (the server enforces both, not just the extension). Phone is evidence only: it becomes a `phone` claim on the created person (there is no person column for it), shown with the record's other evidence; it is never a dedupe key.

The server canonicalizes the URL itself and trusts nothing about it from the page:

- `linkedin`: `normalizeProfileUrl` must yield `/in/<id>` (the lead capture rules: linkedin.com or subdomain, id case preserved). Canonical URL `https://www.linkedin.com/in/<id>`. Anything else is 400 with a sentence naming the accepted shape.
- `x`: host `x.com`, `twitter.com`, `www.` or `mobile.` variants; the first path segment is the handle and must match `^[A-Za-z0-9_]{1,15}$` and not be a reserved path (`home`, `explore`, `notifications`, `messages`, `search`, `settings`, `i`, `compose`, `intent`, `login`, `signup`, `about`, `tos`, `privacy`, `jobs`, `hashtag`, `share`, `download`, `account`, `logout`, `lists`, `bookmarks`, `help`, `verified`, `grok`; the list tracks the site and an unlisted reserved name degrades to a junk capture the user can delete, never an error). Canonical URL `https://x.com/<handle>` with the handle's case kept; the dedupe key lowercases it because handles are case insensitive.

Dedupe, before any write: an existing person whose `linkedin_url` column normalizes to the same `/in/<id>` (for linkedin), whose `x_url` column has the same lowercased handle (for x), or whose email equals the captured email (case folded); the indexed columns replaced the former claim scan (migration 018 backfilled them from claims). A URL hit answers 200 `{ outcome: 'existing', person: { id, name } }` and writes nothing. A new person's canonical profile URL is written to the matching column as well as to its claim. An email hit answers the same, but also saves the canonical profile URL onto the matched person (column plus claim) when that person has no claim for that field yet; the column write bumps the person's version with the `claim.create` audit row as its trail, so a sheet open on that person at that moment can see one version conflict (same transaction, same claim shape as a created capture, written through the standard claim machinery, so the usual `claim.create` audit row and the person's `record_updated` frame follow; no capture specific event is added), so the next lookup and capture recognize the profile instead of forgetting it. Apart from that, capturing someone already in the CRM adds no new fields; the record is edited in the app. Rows staged in pending imports are not checked here; import accept time dedupe already skips a staged row whose email or profile matches a person that exists by then. Identity is the profile, so the same human captured on LinkedIn and then on X becomes two people, merged by hand like any other duplicate; LinkedIn ids that differ only in case also stay distinct, matching lead capture's rule. The canonical LinkedIn URL is built from the raw path segment, percent encoding kept, so it round trips through the same normalization on the next capture.

Captured text is third party content. Control characters, bidirectional override characters, zero width characters, and NUL are stripped from every field (the bio keeps its line breaks), and a name that is empty once invisible characters are gone is rejected, which also keeps the FTS index's no NUL assumption true. The capture note and claims reach the same model facing surfaces as imported claims and CSV fields do, framed there as data, and nothing a model reads from them can send anything without the usual approvals.

A new person answers 201 `{ outcome: 'created', person: { id, name } }`, created in one transaction: `splitName(name)`, title from headline, location, email when free, tags `captured` and the source name. No organization is created; company text becomes a claim only, because a headline fragment is too weak evidence to create or match an organization against. Claims written for name, title, company, location, email, website, and `linkedinUrl` or `xUrl` (the canonical URL): `source_type` `extension`, source URL the canonical profile URL, extraction method `extension:linkedin` or `extension:x`, status `imported`. One activity note records the capture (`Captured from LinkedIn <canonical url>.` plus the bio as a paragraph when present). Audit event `capture.person`, SSE `record_updated`.

`POST /api/capture/verify` (token required, empty body) answers `{ ok: true, workspace }` and is what the extension's options page calls to test the connection.

`POST /api/capture/lookup` (token required, zod strict `{ source, url }` with the same URL rules as capture) answers 200 `{ exists }`, a boolean and nothing else; the button needs no more, so the matched person's fields stay in the app. It applies the capture dedupe rules minus email, which is unknown at lookup time: the `linkedin_url` column normalizing to the same `/in/<id>`, or the `x_url` column with the same lowercased handle, answered by the indexed columns rather than a claim scan. It is read only: no writes, no audit event, no SSE frame. The extension calls it once per viewed profile so the button can show that the person is already in the CRM; a lookup failure of any kind is silent and leaves the button in its idle state, because capture itself remains the authority. The background worker sends this automatic lookup only when the stored server address is a loopback host; with any other address nothing leaves the machine until the user clicks the button, keeping the shipped promise that viewing pages sends nothing off this computer.

### The extension

Layout: `manifest.json` and `options.html` at the extension root referencing bundled `dist/` scripts; `npm run build --prefix apps/extension` bundles with esbuild (and generates the toolbar icons deterministically at build time, so no binaries are committed); load unpacked points at `apps/extension`. Permissions: `storage` only. Host permissions: `http://localhost/*` and `http://127.0.0.1/*` (match patterns cannot name ports, so this covers any local port). Content scripts run on `https://www.linkedin.com/*`, `https://x.com/*`, and `https://twitter.com/*` variants at `document_idle`.

The content script decides whether the current URL is a profile page with the same rules the server enforces, renders one button in a shadow root (the host pages' CSS never touches its contents), and re-evaluates on SPA navigation (location polling plus `popstate`, because neither site reloads the page). The button mounts inline next to the profile name when that anchor exists and falls back to a floating chip in the bottom right corner when it does not, so selector drift moves the button, never removes it. The anchor is the first heading inside `main` whose trimmed text equals the extracted name, else the first `h1`, else the first heading inside `main` (LinkedIn's top card name is an `h2` with rotating obfuscated classes); on X it is the `UserName` test id. On LinkedIn the button then prefers the end of the name line: the last leaf in the top card whose whole text is a connection degree (`· 2nd`, `· 3rd+`) marks the name line's trailing element (its topmost branch below the common ancestor with the heading), and the button is inserted after that, so it sits to the right of the degree marker; with no degree leaf the button follows the name itself. Inline, the button is a compact icon (the extension's capture bracket mark, drawn as SVG in the shadow root) with an accessible label and tooltip; floating, it keeps the full labeled chip for discoverability. Both keep one outer size across every state. The host element carries inline styles only, is inserted after any interactive ancestor of the anchor (a link, a button, or an element with a link or button role) so a click or key press on the button never reaches one, and the button keeps one outer size across the idle and `In CRM` states so a page script cannot read the lookup answer out of layout. Key events do not bubble from the button into the page. The SPA poll also re-mounts the button when a site re-render detaches it; synthetic `popstate` events a page script dispatches are ignored (`event.isTrusted`). The capture sends the address bar's origin and path only, never the query or fragment, so tracking parameters neither leak nor overflow the server's URL limit. Because these sites swap pages in place, the document head can briefly describe the previous profile: a head signal that names a different profile than the address bar (JSON-LD url or og:url on LinkedIn, the header handle on X) drops that layer and degrades toward the floor instead of capturing another profile's fields. A capture on an interstitial or error view can still degrade to the profile id as the name; that is visible and correctable, never silent corruption of another record. Extraction is layered and each layer is a pure function over the document, unit tested against fixture HTML. The signed in LinkedIn SPA serves no JSON-LD, no Open Graph tags, and no `h1`, and its class names are obfuscated and rotate (verified live, 2026-11), so class selectors are banned; the layers are JSON-LD `Person`, then `og:title`, then the first `h1` (these three still cover logged out and older markup), then the top card heading (the first heading inside `main`, preferring one whose text a sibling layer corroborates), then `document.title` with a leading `(N)` notification count stripped and the ` | LinkedIn` suffix required and removed (the whole remaining text is the name, never split on ` - `, which only the og:title format carries; the NOT_A_NAME rejects apply), with the guaranteed floor of the `/in/` id as the name. Two guards bound the top card layer: when a title name exists and no heading matches it (a profile subpage such as `/details/experience/`, whose first heading is a section title), the whole top card layer is skipped, name, headline, and location together; and when the top card's own links name `/in/` profiles and none of them names the address bar's id (a stale card during an SPA swap; a legitimate card can link mutual connections, but it always also links its own profile through the Contact info link), the layer is dropped the same way. Headline and location come from the top card's text lines: the lines after the name, skipping connection degree markers (a short whole line such as `· 2nd`, digit plus ordinal suffix, never a line that merely starts with one) and follower or connection counts (shape based, a number plus a word, so localized counts also filter); the first substantive line is the headline and the last remaining line before `Contact info` is the location. Text line parsing is position based, not label based, so it survives class churn. X reads the profile header test ids with the floor of the handle from the URL and the name from `document.title` (its leading `(N)` count is tolerated). The brittle layer failing degrades the capture, never breaks the button.

When the LinkedIn contact info overlay is open at click time, the capture also reads it: email from a `mailto:` href (query stripped), phone from the value line under the `Phone` label (the parenthetical kind such as `(Mobile)` dropped; a phone needs a digit and at most 40 characters), and website from the first value line under `Website` or `Websites`, taking the text before any ` (` qualifier and prepending `https://` when schemeless. "Open" requires BOTH signals: the address bar is on `/in/<same id>/overlay/contact-info/` AND a visible container headed `Contact info` exists (the last visible one wins, matching where the site appends the real overlay; hidden and fully transparent containers are ignored, and one naming another profile is ignored). The capture never opens the overlay; it reads what the user chose to show. External links in the overlay are wrapped in LinkedIn's redirect, so the visible text is the source of truth for websites. Honest limits, accepted and documented rather than pretended away: the overlay labels are read in English only (a localized overlay is simply not read, nothing breaks), and a script running in the page can fabricate overlay content, the same trust class as every other scraped field; the sharpest edge is a fabricated email, which is a dedupe key, so it can attach this profile's URL claim to the existing person holding that email. That write is visible in the record's evidence and correctable, never silent corruption beyond it.

The content script never sees the token. It messages the background service worker, which reads `{ baseUrl, token }` from `chrome.storage.local` (local, not synced off the machine) and makes the one fetch. Button states: idle, sending, `Added`, and an error state whose message names the fix (open the options page when unconfigured or 401), plus a persistent `In CRM` state. On mount the content script asks the background worker to look the profile up (`/api/capture/lookup`); when the person exists the button reads `In CRM` and is inert. A successful capture shows `Added` briefly and settles to `In CRM`; a capture answered `existing` settles to `In CRM` the same way. The button returns to idle only on navigation to a profile that is not in the CRM. Navigation detection keys on the canonical profile identity (the `/in/` id, or the lowercased handle), never the full URL, so query, hash, and subpage changes on the same profile neither reset the state nor repeat the lookup; and a lookup reply is applied only when the address bar still shows the profile it was sent for, so a reply can never paint another profile's state. The options page holds base URL and token fields, a save, and a test connection control backed by `/api/capture/verify`. The toolbar button has no popup; clicking it opens the options page (the service worker listens for `chrome.action.onClicked`).

## CSV import

CSV import reuses the staging, dedupe, review, and accept machinery that Apify uses, so a spreadsheet and a scrape get identical honesty guarantees.

- `POST /api/imports/csv/preview` takes `{ fileName, content }` (UTF-8 text, 10 MB cap) and returns `{ headers, delimiter, rowCount, suggestedMapping, sample }` without persisting anything. Parsing uses csv-parse with delimiter sniffing (comma, semicolon, tab), BOM stripping, and quoted fields. Hard caps: 10 MB and 20,000 rows; beyond them the request fails with `validation`.
- `POST /api/imports/csv` takes `{ fileName, content, mapping }` where mapping assigns each header to one of firstName, lastName, name, email, company, domain, title, location, linkedinUrl, tags, or ignore. At least email or a name field must be mapped. Location may span several columns (joined with a comma) and tags columns are merged; every other field takes the first non empty value when assigned more than once. Content must be valid UTF-8 text; files that decode with replacement characters are rejected rather than staged as mojibake. The route parses and stages the batch and rows synchronously (source_kind `csv`, raw row preserved), creates a run of kind `csv_import` with scope `{ batchId, fileName }`, and returns the run with 201. The run's ledger has four steps, and the first, parse and stage, is already done at creation because staging is synchronous; the worker then validates rows (no name and no email is invalid, with a reason), dedupes with the same rules as Apify, and requests the same `import_review` approval, whose payload carries `fileName` where the Apify payload carries `actorId`. Approve and reject behave exactly as for Apify batches, including per field claims (source_type `import`, source_url null, extraction method `csv:<fileName>`) and tags `csv-import` and `via-<runId>`.
- A `tags` column is split on commas or semicolons and merged into the created record's tags.

## Qualification

Qualification turns the template's criteria into visible, per criterion verdicts. It never writes to records: results live in `qualification_result`, one row per person, so it is a Maintain level action with no approval, and it is audited like every write.

- Config lives in `workspace.settings.qualification` as `{ exclusions, criteria }`, both arrays of Criterion: `{ id, label, target: "person" | "organization", field: title | location | tags | email | name | kind | domain, operator: contains | equals | in | exists, values: string[], enabled }`. Person rules accept title, location, tags, email, name; organization rules accept kind, domain, location, tags, name. `GET /api/qualification` returns it, with `defaulted: true` until a config is saved; `PUT /api/qualification` replaces it after validation and returns the saved config, keeping client supplied ids.
- Evaluation per person: exclusions first; any matching exclusion marks the person excluded with the reason, and the criteria are still computed for transparency. Each criterion returns `matched`, `not_matched`, or `unknown`. A missing field or record is always `unknown`, never a match. Matching is case insensitive, and `contains` matches substrings, including inside tags; the settings UI says so.
- Evidence: when the newest field claim for that field exists, the reason cites its status and age; otherwise the record value is cited as record data with no claim. Fit (matched of total) and completeness (unknown count) are reported separately and never combined into one hidden score.
- `POST /api/runs` kind `qualify` with scope `{}` or `{ tag }` evaluates people in chunks of 200 per transaction with ledger steps (load criteria, evaluate, write results), snapshotting the criteria in the run scope so a config edit mid run cannot mix rule versions. Counts: `processed` people evaluated, `found` people matching every enabled criterion (this can overlap with `excluded`), `flagged` people with at least one unknown, plus `excluded`. Agent origin may start qualify runs without an allowlist, because the run writes only qualification results.
- Results are a snapshot: `computedAt` says when, and editing a person afterwards does not recompute or mark the result stale yet. This is a known limitation; the UI shows the age rather than implying freshness.
- `GET /api/people` gains `sort=fit` (matched desc, then fewer unknowns, excluded and never qualified last) and each list item carries `qualification: { matched, total, unknown, excluded, computedAt } | null`; the UI marks a result "out of date" when the person changed after `computedAt`. `GET /api/people/:id` carries the full result payload: `{ computedAt, excluded, excludedReasons, matched, total, unknown, criteria: [{ id, label, outcome, reason, evidence }] }`.
- The startup fundraising template seeds editable defaults: an exclusion on tags containing do-not-contact, and criteria for organization kind equals fund, title containing partner, principal, scout, or head of, and tags containing seed.

## Model adapter

The model adapter brings real intelligence to chat and drafting while keeping every honesty rule. Users bring their own model access; the product ships none, and everything except model calls keeps working without it. Five providers are supported, each its own connector kind with the same secret rules: `anthropic` (the reference implementation below), `openai`, `deepseek`, `zai` (GLM), and `ollama` (a local server, no key). Exactly one configured provider is active at a time, chosen in Settings and stored in `workspace.settings.modelProvider`; chat and drafting use the active one, and every `model_call` row records the provider and model.

Provider presets (API facts read from each provider's live documentation on 2026-11-02; prices are list prices per million tokens and every cost shown is an estimate labelled with that date):

- Connector kind `anthropic`: `PUT /api/connectors/anthropic` takes `{ token?, model? }`, validates the token against the models endpoint, and stores it with the same secret rules as Apify (local secret column, masked to last four, never in logs, audit, SSE, errors, or MCP). Settings hold the chosen `model`. `DELETE` removes it. The provider base URL is `https://api.anthropic.com`, overridable with `AGENTCRM_ANTHROPIC_BASE` for tests.
- Supported models with their current list prices per million tokens (a static map in code, used only for estimates and labelled as estimates): `claude-opus-5-5` (default, input 4.00, output 20.00), `claude-sonnet-5-5` (2.00, 10.00), `claude-haiku-5-5` (0.10, 0.50 up to 100K prompts). The default model is Opus 5.5.
- Every model call writes a `model_call` row: a pending row goes in before the provider call and is finalized with real usage after, so a crash mid call leaves a visible "outcome unknown, possibly billed" record and that person is never silently re billed. Estimates use the price map including cache writes at 1.25 times input and cache reads at a tenth; costs shown in the UI always say estimated.
- Chat and drafting send record contents (people, organizations, claims, notes) to Anthropic; the connector card and the draft sheet say so plainly.
- Agent origin draft runs with no budget get a default budget of 1.00 dollars. Draft calls run with SDK retries off (the worker owns the 3 attempts), and a run stops early as partial after three consecutive identical non retryable rejections.

Chat with a model connected: `POST /api/agent/message` accepts `{ text, history?, context? }` where history is up to the last 10 `{ role, text }` turns and context is an optional `{ entityType, entityId }`. The server runs a bounded tool loop (at most 5 tool rounds, 30 second provider timeout) with read only, strict schema tools: `search_crm`, `get_record`, `today_summary`. The model never gets a tool that writes. CRM content enters prompts as data with an explicit instruction that it is not instructions. The reply returns `{ reply, actions, modelConnected: true, usage: { inputTokens, outputTokens, estimatedUsd } }`; suggested actions always come from the server's rule based code, never from model text. A provider failure returns the deterministic reply with `modelFailed: true` and a plain note. With no key configured, the deterministic replies remain exactly as they are.

Run kind `draft_outreach`: scope `{ personIds?, tag?, instructions?, maxPeople (default 10, cap 25), budgetUsd? }`.

1. Load the audience: people with an email, not excluded by qualification, never tagged do-not-contact. Skipped people are counted with reasons.
2. Draft one person per model call with structured output (subject, body, factsUsed citing the record fields and claims the draft used). The system prompt carries the user's instructions and voice, marks CRM content as data, and is cache stable across the batch. Progress checkpoints in the run scope so a restart never redrafts paid work.
3. A refusal or per person failure marks that person flagged with the reason and continues. The budget is checked between drafts: when the spend so far plus the average cost per call would cross `budgetUsd`, the run stops drafting and finishes `partial` with honest counts. The first draft always runs, and a costlier than average draft can push the total past the budget; the UI says so.
4. Final step creates an approval of kind `draft_review` whose payload carries the full drafts (person, subject, body, factsUsed) plus the count and estimated cost, so the approval hash binds exactly what the user read to what gets applied. The UI renders every draft for reading before the decision; facts are labelled as reported by the model, with a server check marking any fact value not found in the record. The run enters `waiting_approval`. The run enters `waiting_approval`. Approving writes one `email_draft` activity per draft, labelled as a draft that was not sent (no email connector exists). Rejecting cancels the run. Nothing is ever sent. Removing the connector fails queued, running, or paused draft runs with a clear step detail before the key is deleted; runs already waiting for review stay decidable.

Counts for draft runs: `processed`, `found` (drafted), `flagged` (skipped or failed, with reasons), plus `estimatedUsd` observed. Agent origin may start `draft_outreach` under the same one active agent run rule as Apify; drafting spends the user's model budget, so the cap applies.

API facts the implementation must follow (current as of this writing): thinking is always on for these models, so the `thinking` parameter is omitted; depth is controlled with `output_config.effort` (`low` for chat, `medium` for drafting). Forced `tool_choice` `any` or `tool` returns a 400 on these models; tools use `auto` with `strict: true` schemas. Structured outputs use `output_config.format`. Refusals surface as HTTP 200 with `stop_reason: "refusal"`; server side fallbacks are enabled with `fallbacks: "default"` plus the beta header `server-side-fallback-2026-07-01`. The stable system prompt carries a `cache_control` breakpoint so batch drafting reuses the prompt cache.

## Mail providers

Sending and inbound sync run through one adapter interface so every provider obeys the same approval, suppression, cap, and honesty rules. A mail provider implements: `submit(intent, message)` returning provider message and thread ids or throwing a typed error; `reconcileUnknown(intent)`, called on the reconcile schedule after an unknown outcome, returning accepted (with ids), not found, or unavailable; `listInbound(cursor)` returning normalized messages (`providerMessageId`, `from`, `to`, `subject`, `text`, the `Message-ID`, `In-Reply-To` and `References` headers, `receivedAt`) plus the next cursor; and an account check. The send intent state machine, preflight, recheck before submit, daily caps, suppression, reply and opt out handling, and the rule that agents can never send are provider independent and live outside the adapters.

Connector kinds `agentmail` and `gmail` are mail connectors (migration 012 widens the connector CHECK and adds `send_intent.provider`, default `agentmail`, plus `send_intent.message_id_header`). Several mail connectors may be configured; exactly one is in use for sending and inbound sync, stored as `workspace.settings.mailProvider`, set automatically on first connect and switchable in Settings with the same "Use this provider" pattern as model providers. Mail readiness means: the in use connector is connected and has a sending address. Preflight and submit recheck read the in use connector; removing it blocks open intents with the existing reason. Intents carry the provider that staged them and are submitted and reconciled only by that provider; switching providers does not re-route open intents, and queued intents staged for a removed or switched away provider block with the connector_removed reason rather than silently sending from another account.

Duplicate send protection is per provider, declared by the adapter:

- `agentmail`: provider idempotency keys (the intent id). Reconcile may retry the same request with the same key within the provider's roughly one day window, which cannot double send.
- `gmail`: no provider idempotency exists, so the app relies on a self generated `Message-ID` (`<ac-{intentId}-{random}@{sender domain}>`) persisted on the intent in its own transaction before the submit request leaves the process. Reconcile after an unknown outcome is READ ONLY: it searches Gmail with `rfc822msgid:` for that header; found means accepted (ids recorded), not found keeps the intent unknown and re-checked on the schedule for a day, after which it stays unknown with a task telling the user to check Gmail's sent mail. A Gmail submit is never retried, because a second POST could send a second email.

## Gmail connector

Connector kind `gmail`. Each user creates their own Google Cloud OAuth client (Desktop app type) and pastes its client id and client secret into the Gmail card; the walkthrough lives in docs/connect-gmail.md and the card links it. This is the honest self hosted pattern: the app never ships a shared client, mailbox access stays first party between the user and Google, and the card states the two consequences plainly: a client left in Testing status expires its consent every seven days (add yourself as a test user and sign in again weekly), and publishing it as In production without verification shows Google's unverified app warning during sign in. Scopes requested, both named on the card: `gmail.send` (sending) and `gmail.readonly` (replies, bounces, and the duplicate protection search; Google classes it restricted, which is fine for a client you own). Tokens are stored unencrypted in the local database like every other secret, with the same sentence on the card.

- OAuth: authorization code with PKCE (S256) and a state nonce, authorization URL `https://accounts.google.com/o/oauth2/v2/auth`, token endpoint `https://oauth2.googleapis.com/token`, redirect `http://127.0.0.1:<api port>/api/connectors/gmail/oauth/callback` (loopback, allowed for Desktop clients). `PUT /api/connectors/gmail` stores `{ clientId, clientSecret }`; `POST /api/connectors/gmail/oauth/start` returns the authorization URL and persists the pending state and verifier; the callback consumes the state before any network call, exchanges the code, reads the account's address and current `historyId` from `users.getProfile`, stores tokens, address, the history cursor, and `settings.oauthCompletedAt` (the web detects success by it), and redirects the browser to the connectors page. A callback with a wrong or unknown state records nothing on the connector and only redirects with an error code. `DELETE` behaves like removing AgentMail. Access tokens are refreshed ahead of use with compare and set saves, so a sign in that completes during a refresh is never overwritten; `invalid_grant` marks the connector error with the sentence about Testing mode consents expiring after seven days, and a connector coming back resumes the read only reconciles of its unknown intents. Connecting a second mail provider never moves sending: the provider already in use is persisted first, and `POST /api/mail-provider` refuses a connector whose account is not ready.
- Base URLs `https://accounts.google.com`, `https://oauth2.googleapis.com`, and `https://gmail.googleapis.com`, each overridable (`AGENTCRM_GOOGLE_AUTH_BASE`, `AGENTCRM_GOOGLE_TOKEN_BASE`, `AGENTCRM_GMAIL_BASE`) for tests.
- Submit: the app composes a plain text RFC 2822 message (From, To, Subject, Date, Message-ID, MIME-Version, Content-Type text/plain charset utf-8, and In-Reply-To plus References when replying in a known thread), base64url encodes it, and POSTs `users/me/messages/send` with `{ raw }` (plus `threadId` for replies). The response ids map to `provider_message_id` and `provider_thread_id`. A 401 refreshes the token once and retries, which is safe because Google rejected the request before accepting any mail; a definitive 4xx fails the intent with the reason, except 429, which is treated as an unknown outcome because Google may have accepted the message before throttling the response; a timeout or 5xx is an unknown outcome. Unknown outcomes are handled by the read only reconcile above on a schedule spread over roughly a day.
- Inbound: poll `users.history.list` from the stored cursor with `historyTypes=messageAdded` and `labelId=INBOX`, fetch each new message with `users.messages.get` (format full), normalize, and advance the cursor only after the batch is stored. A 404 on the cursor (expired history) resets the cursor to the account's current `historyId` and writes an honest connector status note that a sync gap may have skipped replies in between. Polling uses the existing mail poll interval and backoff rules.
- Bounces: Gmail has no bounce API. Inbound messages from a mailer daemon or postmaster are parsed conservatively: the intent is marked bounced, with the usual suppression row and task, only when the message carries the original self generated `Message-ID` AND a failure signal: an attached delivery status report whose Action is failed, or failure wording without delay wording when no report is attached. Delay, delivered, and relayed notifications stay ordinary inbound messages; anything less certain does too.
- Caps: the app's own 50 accepted sends per inbox per day applies unchanged, and the card notes Google's own daily limits (consumer accounts around 500 recipients per day, Workspace higher) without promising them.

## Microsoft 365 connector

Connector kind `microsoft`. Each user creates their own Entra app registration and pastes its client id into the Microsoft card (no secret: it is a public client with PKCE); the walkthrough lives in docs/connect-microsoft.md. Registration requirements the walkthrough spells out: supported account types "Accounts in any organizational directory and personal Microsoft accounts", a Mobile and desktop platform with the redirect `http://localhost` (Microsoft ignores the port for loopback matching), and Allow public client flows set to yes. Works with personal outlook.com and work accounts through the `/common` authority; a work tenant that requires admin consent for the scopes surfaces Microsoft's own error sentence on the card rather than a silent failure.

- OAuth: authorization code with PKCE at `https://login.microsoftonline.com/common/oauth2/v2.0/{authorize,token}`, redirect `http://localhost:<api port>/api/connectors/microsoft/oauth/callback`, scopes `offline_access Mail.ReadWrite Mail.Send User.Read` (the last only to read the account's address at sign in). The callback follows the Gmail rules: state consumed before any network call, forged callbacks record nothing, `settings.oauthCompletedAt` set only on success. Refresh tokens rotate on every use; the replacement is stored with the same compare and set discipline as Gmail, so a sign in completing mid refresh is never overwritten. Revocation or expiry marks the connector error asking to sign in again, and recovery resumes reconciles. Base URL env overrides `AGENTCRM_MS_LOGIN_BASE` and `AGENTCRM_GRAPH_BASE`; `AGENTCRM_MS_TIMEOUT_MS` overrides the request timeout for tests. Migration 013 adds the connector kind and `send_intent.provider_draft_id` (the immutable draft id; `message_id_header` stores the `internetMessageId`).
- Submit is draft first, because `sendMail` returns nothing and offers no duplicate protection. For a new message the app creates a draft (`POST /me/messages` with `Prefer: IdType="ImmutableId"`, the content, and a custom `x-agentcrm-intent` header carrying the intent id), persists the returned draft id and `internetMessageId` on the intent in its own transaction, re-runs the full recheck (payload hash, suppression, reply since approval, cap, connector, account, provider in use) immediately before the send, writes a send attempt timestamp in its own transaction, then `POST /me/messages/{id}/send`. Replies are not implemented yet: every send is a new message, and nothing calls `createReply` today. Reconciling an unknown SEND outcome reads the draft by its immutable id. Acceptance requires the message to actually sit in Sent Items (or be found there by `internetMessageId`); a message in any other folder keeps the intent unknown. A message that is still a draft gets the ONE sanctioned resend, under all of these guards: the full recheck passes again at that moment, the approval is still under a day old, the connector was never removed since the attempt (removal marks the intent read only check forever), the send attempt timestamp shows a quiet period longer than twice the request timeout plus thirty seconds (fail closed on anything missing or unparseable), and the draft's recipients, subject, and body still EXACTLY match the approved message, because a draft sitting in Outlook can be edited; a mismatch never sends, stops the checks, and tells the user to delete the changed draft and stage again. Sending the same unchanged draft again cannot double send. An unknown CREATE outcome scans the drafts folder's recent messages for the `x-agentcrm-intent` header and adopts the draft only when its content matches the approved message; at worst a stray draft is left behind, never a second sent mail, and the step detail says so.
- Inbound: per folder delta on the Inbox (`/me/mailFolders/inbox/messages/delta`), starting from the sign in time, storing the cursor (`start:<time>`, `next:<url>`, or `delta:<url>`; links on a host other than the Graph base are refused so the bearer token cannot leak) and following nextLinks with a per poll page cap and continuation; `syncStateNotFound` or 410 restarts the folder's sync with an honest connector note about the possible gap. Throttling honors `Retry-After` by moving the next poll out. Ordinary inbound messages skip header fetches; only mailer daemon and postmaster messages get their headers and delivery status attachments fetched (bounded retries) for the shared bounce evidence rules.
- Bounces: non delivery reports arrive as ordinary inbound messages; only a report that carries the intent's stored `internetMessageId` (or the x header) marks the intent bounced, with the usual suppression and task.
- The card notes Microsoft's own limits in one sentence (10,000 recipients per day per mailbox, 30 messages per minute on Microsoft 365; personal account limits are not published) without promising them. The app's 50 per day cap applies unchanged.

## IMAP and SMTP connector

Connector kind `imap`: the compatibility path for providers without a first party API, shipped with two tested presets (iCloud Mail, Fastmail) and a custom mode. Dependencies: nodemailer 10 (MIT-0) for SMTP and imapflow 2 (MIT) for IMAP, both wrapped behind one transport seam (`providers/mailTransport.ts`: connect and verify, send, search the Sent mailbox by Message-ID, append to Sent, list new inbox messages by UID) so the pipeline is testable against a stubbed seam; the README says the connector is verified against that seam, not against live servers.

- Settings: `preset` (`icloud`, `fastmail`, `custom`), the sending address, username, app password (stored like every secret), IMAP host and port, SMTP host, port and TLS mode, the detected or chosen Sent mailbox, and per mailbox cursors `{ uidValidity, lastSeenUid }`. Presets fill the servers: iCloud `imap.mail.me.com:993` and `smtp.mail.me.com:587` (STARTTLS), where the IMAP username is the address's local part while SMTP uses the full address, which the preset handles; Fastmail `imap.fastmail.com:993` and `smtp.fastmail.com:465` (TLS). Each preset's card hint names where the app password is created (Apple: account.apple.com, Sign-In and Security, App-Specific Passwords, two factor authentication required; Fastmail: Settings, Privacy & Security, New app password) and Fastmail's rule that the Basic plan has no IMAP or SMTP access. Connecting verifies the IMAP login, lists mailboxes to find the Sent special use (overridable), and verifies SMTP; what was verified is stored and shown. A working connector is protected from bad edits: a new app password that fails the checks is not kept (the stored one stays, and the sentence says so), and a chosen Sent mailbox that does not exist changes nothing (the previous one stays, with a sentence naming the server's mailboxes), so one typo never blocks approved mail. A temporary SMTP login refusal (a 4xx such as 454) fails only that message and never marks the saved login rejected. Reconnecting the same address, including after a removal, resumes the read only checks of unknown messages.
- Submit: the Message-ID is generated and persisted on the intent in the claim transaction, the full recheck and the send attempt stamp run like the other providers, and the same composed bytes go to SMTP and to the Sent copy. Outcome classification: a permanent 5xx reply fails the intent with the server's sentence; a failure before the message data started is a plain failure (nothing was sent); a lost connection, timeout, or unreadable reply after data started is unknown, and a 4xx reply to the end of the message is also treated as unknown rather than failed, because some servers accept despite it. An accepted submission is followed by a best effort IMAP APPEND of the same bytes to the Sent mailbox (skipped with a note when the server reports storing its own copy; when that is unknown, which is the normal case, the append runs with a note that Sent may show the message twice; the recipient's mail is never affected). Reconcile is read only with no resend exception at all: search the Sent mailbox for the Message-ID header (exact match after the search), found means accepted, not found keeps the intent unknown, because neither preset documents whether its SMTP stores a copy on its own. Past the window it stays unknown with a task naming the provider's webmail Sent folder. Nothing is ever resent with the same or a new Message-ID. The Message-ID doubles as `provider_message_id` and `provider_thread_id`, so replies link by thread. Env overrides: `AGENTCRM_IMAP_TIMEOUT_MS` (request deadline) and `AGENTCRM_IMAP_FAKE=1` (a deterministic in process transport with debug only routes for manual checks; never on in a normal run).
- Inbound: poll the Inbox by UID above the stored `lastSeenUid` (stored as the string `uidValidity:lastSeenUid`, initialized from the Inbox position seen at connect), guarding `uidValidity`: a change discards the cursor, resets to the mailbox's current `uidNext`, and writes the honest gap note. The cursor advances only after the batch is stored. One connection per operation, closed after, which respects Fastmail's published login rate limits.
- Bounces: delivery status notifications (multipart/report, report type delivery-status) are parsed conservatively; only a report whose returned headers carry the intent's Message-ID marks it bounced. Plain mailer daemon messages without it stay ordinary inbound mail.
- Sending limits per preset are stated on the card from the providers' documentation (Fastmail publishes per plan daily caps and counts each recipient; Apple publishes none), never promised. The app's own cap applies unchanged.

## Email: the AgentMail connector and sending

Email is the only place AgentCRM touches the outside world on the user's behalf, so it carries the strictest rules in the product. Nothing is ever submitted to the provider without a human approving the exact frozen message, and an unknown outcome is surfaced, never resolved by guessing.

Connector kind `agentmail`: API key (`am_...`), validated against the API, stored under the same secret rules as the other connectors. Settings hold the selected inbox (`inboxId`, `email`) and sync cursors. The user picks an existing inbox from a list or explicitly creates one (optional username; creation uses the provider's `client_id` idempotency). Base URL `https://api.agentmail.to/v0`, overridable with `AGENTCRM_AGENTMAIL_BASE` for tests. Provider facts the implementation relies on: Bearer auth; `POST /v0/inboxes/{inboxId}/messages/send` with an `Idempotency-Key` header where a retry with the same key returns the original `message_id` and `thread_id` and sends no second email, and the same key with a different payload returns 409; `GET /v0/inboxes/{inboxId}/messages` with `after` plus `ascending=true` and `page_token` for inbound sync, message direction read from the `received` and `sent` labels; `GET /v0/inboxes/{inboxId}/messages/{messageId}` for full bodies; `GET /v0/inboxes/{inboxId}/events` (label.added, label.removed, newest first, no after filter, so the poller pages until it meets a seen event id) for bounce evidence via the `bounced` label. List response shapes are not fully documented, so the adapter parses defensively. No public webhook is used; everything is outbound polling, every poll interval default 60 seconds (`AGENTCRM_MAIL_POLL_MS`).

The send intent state machine, per the product spec:

- "Prepare to send" on a saved draft (one person) or on a draft run's detail (all its drafts) creates a run of kind `send_outreach` holding the intents in `awaiting_approval` plus one approval of kind `send_review` whose hashed payload is `{ messages: [{ intentId, personName, to, subject, body, inboxEmail, provider }], excluded: [{ personName, toEmail, reason }], remainingDailyCap, mailProvider, runId? }` (the provider fields are additive; payloads approved before they existed still verify and render). When a follow-up plan was attached, the payload also carries `followups: { steps: [{ waitDays, body }] }` (additive in the same way). Exclusion and block reasons use the codes suppressed, demo_address, invalid_recipient, duplicate_open_intent, no_inbox, daily_cap, reply_received, connector_removed, followup_armed (the person already has an active follow-up rule; stop it to stage again), and followup_stopped (the step's rule was stopped after the step was created). Preflight at creation excludes, with listed reasons: suppressed addresses, demo addresses (example.com, example.org, example.net and subdomains are blocked with reason demo_address so synthetic data can never generate real mail), missing or invalid recipient, an already open intent for the same person and subject, no connected inbox, and no room in the daily cap.
- Approving moves the intents to `queued`. Editing anything invalidates the approval (hash mismatch refuses the decision). Cancelling a single intent before the decision is subtraction only: approve then queues only the intents still awaiting whose message matches the approved payload and reports the cancelled ones as skipped; approving when everything was cancelled resolves as a rejection with a note. Rejecting cancels them all.
- The worker submits queued intents one at a time per inbox. Immediately before each submit it rechecks: payload hash against the approval, suppression, a reply arrived from that person since approval (blocks with reason), connector still configured, daily cap. A failed recheck moves the intent to `blocked` with the reason; blocked intents need a fresh human decision, never an automatic retry. A queued intent whose approval is more than a day old is blocked the same way ("Approved more than a day ago. Review and approve again."), and the `send_outreach` run stays running until every intent settles, then resolves honestly (partial when anything failed, bounced, blocked, or stayed unknown).
- Submit uses the intent id as the `Idempotency-Key`. Success stores `provider_message_id` and `provider_thread_id`, sets `accepted`, and writes an activity on the person that says provider accepted, which is not delivery. A definitive 4xx sets `failed` with the reason. A timeout, network failure, or 409 sets `unknown`; reconciliation retries the same request with the same key on a backoff schedule, which the provider's duplicate protection makes safe for about a day after the attempt. Past that window the intent is never retried: it stays `unknown` with a task telling the user to check the provider's sent mail. An intent that is `unknown` never becomes `failed`, and nothing is ever resent with a new key.
- Daily cap: 50 accepted sends per inbox per day (server local day), checked at preflight and at submit, with the remaining budget shown in the UI. 25 intents per approval at most.

Inbound sync: the poller fetches new messages after the cursor, dedupes by provider message id, stores them, links them to people by sender address, and fetches full text for inbound messages. A message on an accepted intent's thread (or from a person with open intents) marks that intent `replied`, creates a task to respond, and blocks any queued or approved intents to that person. Inbound text matching opt out wording (unsubscribe, stop, opt out, remove me) creates a suppression row with reason opt_out plus a review task; the suppression applies immediately and a human can lift it. The events poller maps a `bounced` label to the intent (`bounced`), writes a suppression row with reason bounce, and creates a task. Open tracking is off: `track_opens` is never sent, and opened labels are ignored.

Agents never touch sending: MCP and the chat endpoint cannot create, approve, or submit send intents, and the CLI refuses to decide send_review approvals because it cannot show the full messages. Sending is a human flow through the UI, enforced by the backend. Inbound email content is excluded from every model facing surface (draft prompts, chat tools, MCP record reads); it appears only in the human UI.

### Follow-up rules

A follow-up rule sends pre-approved nudges when a recipient has not replied. The rule is the thing the human approves: the exact text of every follow-up, the waits, and the stop conditions are frozen into the send_review payload, so the one decision covers the first message and everything that may follow it. Nothing about a follow-up is composed, scheduled, or sent by a model; agents cannot create, decide, or stop rules (no MCP tool, no chat action, and the CLI refuses).

- Staging: `POST /api/send-intents` accepts an optional `followups: { steps: [{ waitDays, body }] }`. One or two steps; `waitDays` is an integer 1 to 30; `body` is plain text, 10 to 2000 characters after trimming. The same step text goes to every recipient in the batch verbatim, and the review says so. No placeholders or tokens are substituted.
- Approving queues the first messages exactly as before and creates one `followup_rule` per queued intent (status `waiting`), carrying the frozen steps, the approval id, and the anchor intent's provider. Rejecting, or cancelling an intent before the decision, creates no rule for it.
- Arming: when the anchor intent reaches `accepted`, the rule arms and `next_due_at` is the acceptance time plus `waitDays` days; a due time landing on Saturday or Sunday slips to the following Monday at the same time (server local). A rule whose anchor settles any other way (failed, blocked, cancelled, replied, bounced, or acknowledged) stops without sending, reason `not_sent`.
- The worker's follow-up lane ticks on the mail poll cadence and walks rules in `waiting`, `armed`, and `sending`. Stop conditions are checked for every one of those rules at every tick, due or not, so a reply stops an armed rule at the next tick instead of sitting behind a due date the UI keeps showing. A due armed rule creates its step only after the in use provider's inbound sync has completed successfully at a time after the step's due time; until then the rule simply waits, because sending before looking at the mailbox could nudge someone who already replied (a machine that was off or a poll that keeps failing therefore delays follow-ups rather than risking one, and a rule that stays overdue past the window expires with its task). The step's send intent is created in the claim transaction with a compare and set on the rule's status and step, so two ticks can never create the intent twice. The created intent is born `queued` with the rule's `approval_id`, `followup_rule_id`, and `followup_step` set, subject `Re: <anchor subject>` (not doubled when the subject already starts with Re:), body the frozen step text, payload_hash over the created message, and the anchor's provider. The rule moves to `sending`.
- Stop conditions: any inbound message linked to the person received after the anchor was submitted stops the rule (`replied`); a suppression for the address, whatever its reason, stops it (`suppressed`); a bounce on the anchor or a previous step stops it (`bounced`); the anchor's provider no longer being the connector in use, or its connector being removed, stops it (`connector_changed`); a human stop stops it (`stopped_by_user`). The per intent submit recheck (payload hash, suppression, reply since approval, connector, cap) still runs unchanged immediately before the actual send, and a queued step whose rule is no longer `sending` blocks there with reason `followup_stopped`, so a stop between tick and submit holds as a second layer.
- One active rule per person, enforced where rules are made, not only at staging: deciding an approval creates a rule for at most the first queued intent per person, and none for a person who already has a rule in `waiting`, `armed`, or `sending`; skipped people are audited and listed in the decision response as `followupSkipped: [{ intentId, personId, personName, reason }]` with reason `same_approval` or `active_rule` (always present on send_review decisions, empty when nothing was skipped). The person sheet shows every active rule, not just the newest.
- Threading: on Gmail and IMAP the step intent carries `replyTo` built from the previous accepted message's self generated Message-ID and thread id (`In-Reply-To`, `References`, and the Gmail `threadId`), so follow-ups land in the same thread. AgentMail and Microsoft have no reply path in their adapters today, so their follow-ups go out as new messages whose subject is `Re: <anchor subject>`, and the review sheet says which behavior applies.
- Caps and staleness: step intents count against the same daily cap. A tick that finds no room in the cap slips `next_due_at` by one day, weekend adjusted like any other due time, instead of blocking. The one day approval staleness rule is replaced for rule created intents by their own creation time: a step intent still queued more than a day after the rule created it blocks with "Created by a follow-up rule more than a day ago." A blocked, failed, or cancelled step stops the rule (`step_not_sent`) with a task. A step more than 7 days overdue, for example because the computer was off, expires the rule (`stopped_reason` `overdue`) with a task saying nothing was sent; a rule still unfinished 90 days after its approval expires with `stopped_reason` `ceiling` and a task saying the plan is too old, and the UI words the two differently.
- Advancing: while `sending`, the tick reads the step intent's state. Accepted with steps remaining re-arms the rule with the next wait measured from that acceptance; accepted with no steps left finishes it (`done`); replied or bounced stops it with that reason; unknown leaves the rule `sending` until reconciliation settles the intent one way or the other. A step left `unknown` after its rule stopped or expired is never submitted again, not even through a provider's idempotent retry; it keeps its unknown task, because the attempt before the stop may or may not have gone out, and only read only checks may settle it.
- Staging preflight excludes a person whose rule is in `waiting`, `armed`, or `sending` with reason `followup_armed`. Removing the in use connector or switching providers stops that provider's active rules with `connector_changed` (the removal response already lists the blocked intents; stopped rules show their reason in the UI). Stopping a rule by hand also cancels its queued step intent. Every rule creation, transition, and stop is audited, and rule changes emit the `followup_updated` SSE frame.
- Honest limits: a reply sent from a different address of the same person, on a new thread rather than ours, is not linked to the person by the existing reply model, so it does not stop the rule; a reply on our thread links whatever address it comes from. A step that comes due while the computer is off is sent on wake if it is less than 7 days late, whichever weekday that wake is; the weekend rule shapes due times, not wake times.

## API contract

Base path `/api`. Responses are JSON with camelCase keys (`firstName`, `expectedVersion`); database columns stay snake_case. List endpoints accept `limit` (default 50, max 200) and an opaque `cursor` (base64url of the last row id, keyset ordered), and return `{ items, nextCursor }` where `nextCursor` is null on the last page. Successful creates return 201. Errors use HTTP status plus `{ "error": { "code", "message" } }`. Codes: `validation`, `not_found`, `version_conflict` (409, with the current record at `error.current`), `conflict`, `unauthorized` (401, only on the token guarded capture routes), `internal`. Duplicate person emails and organization domains return 409 `conflict`.

## MCP server

`npm run --silent mcp --prefix apps/server` (and CLI `crm mcp`) starts an MCP server over stdio using the official TypeScript SDK. The `--silent` flag matters: without it npm prints its script banner to stdout and corrupts the protocol stream. Tools, all workspace scoped and read mostly:

- `crm_describe`: capabilities, template, counts, allowed actions, and `modelProvider: { configured, kind, status, model }`, never a key
- `crm_search`: query with type filter, bounded results
- `crm_get_record`: person, organization, or opportunity by id, with evidence
- `crm_propose_changes`: validate a batch of field changes, return a preview, write nothing
- `crm_apply_changes`: apply a previously validated proposal with expected versions
- `crm_start_research`: start a run and return its id: `demo_research`, `qualify`, `apify_scrape` for an allowlisted actor, or `draft_outreach` (one active agent started run at a time)
- `start_lead_capture`: start a `lead_capture` run from a LinkedIn post URL; every involved actor must be on the allowlist, and it shares the one active agent started run limit
- `crm_get_run`: run status, steps, counts

MCP tools call the same actions as the HTTP routes. No tool can decide an approval.

## Templates

A template defines the vocabulary of a workspace: the pipeline name, the ordered stage names, and the default qualification config. Three templates ship, defined in code in one registry (`templates.ts`), versioned with the app:

| Id | Name | Pipeline | Stages |
| --- | --- | --- | --- |
| `startup-fundraising` | Startup fundraising | Fundraising | Research, Qualified, Introduction or outreach, Meeting, Diligence, Commitment, Closed |
| `fund-lp` | Fund LP fundraising | LP fundraising | Research, Qualified, Introduction or outreach, Meeting, Due diligence, Soft commitment, Subscribed |
| `client-sales` | Client sales | Sales | Research, Qualified, Outreach, Discovery, Proposal, Negotiation, Closed |

Default qualification configs per template follow the same shape as the startup one: `fund-lp` qualifies people at funds, family offices, and other allocators (organization kind `fund`; titles partner, principal, chief investment officer, head of, director, family office; tag `lp`), `client-sales` qualifies buyers at companies (organization kind `company`; titles founder, chief executive officer, chief operating officer, vp, head of, director; tag `prospect`). The do not contact exclusion is in every template. Records, tags, claims, tasks, and history never belong to a template.

- `GET /api/templates` lists `{ id, name, description, pipelineName, stageNames, current }`.
- `POST /api/workspace/template` switches the workspace template in one transaction. Body: `{ template, stageMapping, replaceQualification, expectedVersion }` where `expectedVersion` is the workspace version and `stageMapping` maps every EXISTING stage id to a new stage name from the target template. Every old stage that holds at least one opportunity must be mapped; the server rejects the request naming the unmapped stages otherwise (a stage with no opportunities may be omitted and simply disappears). The transaction renames the pipeline, creates the new stage set in order, moves every opportunity per the mapping writing one `stage_change` activity each (actor `system:template`), deletes the old stages, replaces the qualification config with the target template's defaults when `replaceQualification` is true (otherwise the existing config stays as it is, even where it names tags the new template does not use), updates `workspace.template`, bumps the workspace version (migration 011 adds `workspace.version`), writes one audit event (`workspace.template_change` with from, to, per stage moved counts, and the count of stage history events that pointed at removed empty stages), and emits `record_updated` for the workspace and each moved opportunity. Stage history rows that reference a mapped stage are re-pointed to its replacement; rows pointing only at a removed empty stage are dropped and counted in the audit detail, while the `stage_change` activities keep the real before and after names in text. When `replaceQualification` is false and no config was ever saved, the old template's defaults are saved first so the rules in force do not silently change. A version mismatch is the usual 409.
- Switching back and forth is allowed; nothing is remembered from the previous template beyond the stage history on each opportunity.

## Backup and restore

Two CLI commands (and root npm scripts `backup` and `restore`), documented in the README:

- `crm backup [directory]` writes a consistent snapshot of the live database with better-sqlite3's online backup API (safe under WAL while the server runs) to `<directory or data/backups>/agentcrm-backup-<UTC timestamp>.db`, never overwriting an existing file, and prints the path and size. The backup contains everything, connector tokens included, and the command says so. Relative paths given to backup and restore resolve against the folder npm was run from, so the root scripts work from the repository root.
- `crm restore <file>` replaces the local database with the snapshot. Safety order: it refuses while the API server answers on the configured port (stop the server first); it opens the snapshot read only and checks it is an AgentCRM database whose applied migrations are a subset of the ones this build knows (a snapshot from a newer build is refused by name); it moves the current database files (db, wal, shm) to `data/agentcrm.pre-restore-<UTC timestamp>.db` aside rather than deleting them, then copies the snapshot into place. The next server start runs any pending migrations forward. The command prints what it moved where.

## CLI

Binary name `crm`, implemented in the server workspace, JSON output with `--json`.

```
crm doctor
crm seed [--reset]
crm serve
crm search <query> [--json]
crm runs list [--json]
crm runs get <id> [--json]
crm import <file.csv> [--preview] [--json]
crm approvals list [--json]
crm approvals decide <id> approve|reject [--note <text>] [--json]
crm backup [directory]
crm restore <file>
crm mcp
```

`crm import` with `--preview` prints the parse result and suggested mapping without staging; without it, the suggested mapping is used to stage the file and the command prints the run and batch ids. The CLI runs as the local user, so `crm approvals decide` is a human decision, unlike MCP tools, which can never decide approvals.

`crm seed` fills the database with synthetic demo data and replaces records only, never configuration. The workspace row with all of its settings (the capture token hash, the chosen model and mail providers, a saved qualification config), the pipeline and its stages, and every connector row survive a seed; `--reset`, required once records exist, preserves them the same way. Record ids are deterministic for a given seed date, so two fresh databases seeded with the same date hold identical records; the workspace row itself keeps whatever id it was created with. Seeding writes the template's default qualification config only when none is saved.

Exit codes: 0 success, 1 expected failure with a printed reason, 2 usage error.

## Conventions

- Loopback only. The server binds 127.0.0.1 and additionally rejects requests whose Host header is not 127.0.0.1, localhost, or [::1] (any port) with 403, as a DNS rebinding guard.
- Environment overrides: `AGENTCRM_DB` (database path), `AGENTCRM_PORT`, `AGENTCRM_LOG_LEVEL`, `AGENTCRM_STEP_MS` (demo run step interval), `AGENTCRM_APIFY_BASE` (provider base URL, for tests), `AGENTCRM_APIFY_TIMEOUT_MS` (poll timeout, default 600000), `AGENTCRM_APIFY_POLL_MS` (poll interval, default 3000), `AGENTCRM_ANTHROPIC_BASE` (provider base URL, for tests), `AGENTCRM_ANTHROPIC_RETRIES` (SDK retry count, default 2), `AGENTCRM_AGENTMAIL_BASE` and `AGENTCRM_AGENTMAIL_TIMEOUT_MS` (mail provider, for tests), `AGENTCRM_MAIL_POLL_MS` (inbound poll, default 60000, min 5000), `AGENTCRM_MAIL_RECONCILE_MS` (reconcile schedule override), `AGENTCRM_OPENAI_BASE`, `AGENTCRM_DEEPSEEK_BASE`, and `AGENTCRM_ZAI_BASE` (provider base URLs, for tests; Ollama's address lives in its connector settings).
- Known limitation: keyset cursors compare against the cursor row's sort keys at read time, so a record edited between pages can shift page boundaries for name, date, or recency ordered lists. A composite cursor that freezes the sort key is planned.
- All server code TypeScript, ESM, strict mode.
- Tests with vitest cover the action service: version conflicts, workspace scoping, approval decisions, run transitions.
